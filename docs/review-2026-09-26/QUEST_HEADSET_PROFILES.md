# Quest 3 headset profile comparison

Measured on Meta Quest 3 in Quest Browser with the same `c315e40-2026-09-27T05:12:09.407Z` build, tabletop view and Aerial imagery. Four opt-in JSON sessions were downloaded from the headset on 2026-09-26 (Pacific time). **High runs 1 and 2 and Balanced run 2 used Olympus and Bailey Range June 2026; Balanced run 1 used Mount Rainier via Emmons.** The Rainier run is useful for understanding range but must not be treated as a controlled High/Balanced comparison. The raw session files are kept outside the repository because they include device and route metadata.

These reports record the `satellite` style but did not record the active provider. At the time, the token received Cesium HTTP 403 for the localhost referrer and HTTP 200 for the hosted site's referrer, so Esri fallback is likely for these USB-forwarded sessions. Their measured performance must not be assumed to represent Cesium Bing imagery. The token's localhost permission was subsequently updated, and later reports explicitly record the active provider.

The table uses one-second windows beginning at least five seconds after `xr-session-start`. A *stable* window has 100% selected imagery coverage and no tile requests in flight. Values are medians across stable windows, so they describe typical one-second periods rather than the entire run. The runs were not controlled for pose, movement, thermal state, or background work.

The fast Balanced run used a different route. On the matched Olympus/Bailey route, Balanced's median JavaScript submission p95 was 30.5 ms versus 32.2 and 36.9 ms for High, while median callback cadence was 49.1/s versus 52.7/s and 34.8/s. This small, variable improvement does **not** establish that Balanced solves the slowdowns. Balanced rendered about 16–17% fewer triangles than High on Olympus/Bailey, despite allowing 28 rather than 48 selected imagery patches. The chunk count is a count of retained chunks, not visible chunks. A coverage value of 100% means complete coverage of the **selected** footprint, not identical geographic area or resolution between presets. The headset user reported that the detail loss in Balanced is noticeable.

Several sessions remained slow after network loading finished, so tile downloads alone do not explain the issue. `ImageryLODManager.evaluateLOD` raycasts against the rendered terrain when the inspection pose changes; High evaluates more often and uses more terrain geometry. The first four sessions could not isolate that cost. Build `989c573` added opt-in timings for terrain raycasting, tile selection, and reconciliation; none of the measurements in the table include those timings.

A fifth, 85-second Olympus/Bailey High XR session on build `989c573` confirmed the CPU attribution. Across the recorded session, raycasting averaged 4.64 ms per callback out of 4.90 ms for the entire imagery update (about 95%). In the 58 stable windows at least five seconds after XR entry, median per-callback raycasting was 4.84 ms; the worst individual raycast took 48.9 ms. Tile selection and reconciliation averaged 0.02 ms and 0.16 ms per callback. Median stable-window JavaScript submission p95 was 36.65 ms and callback cadence was 42.0/s. This is still browser CPU timing, not headset GPU time.

Build `47a52a3` tried a bounding-volume hierarchy for those same rendered-triangle hits while preserving the High terrain and imagery budgets. A 74-second Olympus/Bailey High headset session showed lower **stable-window median** raycast cost (0.36 ms per callback), CPU submission p95 (7.6 ms), and higher callback cadence (61.0/s). It also showed recurring raycast spikes around 100–123 ms when the visible tabletop terrain changed, including long stalls well after startup. This version is therefore unsuitable despite the typical-window improvement.

Build `bedc810` replaced the hierarchy with traversal of the terrain's regular grid cells. It checks the same rendered triangles and honors the base mesh's compacted index range, without rebuilding a tree after local DEM promotion. Exact-hit regression tests compare results with Three.js's raycaster across transformed terrain, visible refinement, changed indices and heights, multiple ray angles, and material sides.

An 86.6-second Olympus/Bailey High XR session on `bedc810` confirmed **Cesium Bing** as the active provider and showed imagery evaluation averaging 0.25 ms per callback, including 0.07 ms for raycasting. Grid raycasting removed the earlier recurring raycast stalls. Visual stability remains poor: after the first eight seconds, selected high-resolution coverage fell below 100% in 34 of 76 windows, below 75% in 12, and reached 0% once. The 36 windows with complete coverage and no tile requests had a median callback cadence of 51.0/s and median CPU submission p95 of 7.0 ms; the 24 windows with in-flight imagery requests had 29.1/s and 12.8 ms. The count of resident imagery patches stayed at the Quest High cap of 48, suggesting repeated replacement of the selected working set. Local terrain work exceeded 30 ms in 16 windows and reached 108.8 ms in one callback. The headset user reported that sharp imagery was difficult to obtain and keep visible even while mostly still. This report does not record tile selection changes, patch creation/disposal totals, or cache failures, so it cannot yet separate footprint churn from failed downloads.

The follow-up build stabilizes the geographic tile-selection center near parent-tile boundaries, ignores ambiguous near-vertical gaze directions, and keeps a high-resolution tabletop terrain chunk while the inspected point remains well inside its coverage. It also adds per-window zoom, desired/visible patch, creation/disposal, and cache-failure counters. A matched headset run is needed to verify whether coverage and long stalls improve without reducing High's selected resolution or terrain detail.

A separate 124.8-second High/Cesium session on **Putrid Pete's trek** captured a sharper ridgeline screenshot at about 99 seconds and a visibly degraded one ten seconds later as the user tilted their head up. At both moments the trace reported 100% coverage of the *selected* imagery footprint, zero imagery requests in flight, and about 72 callbacks/s. The draw-call count changed from 118 to 66 while the selected-patch count remained 48. This strongly suggests misplaced focus/selection rather than a network stall: a center gaze ray can pass above a ridge that remains visible lower in the headset view, causing the app to aim imagery and the single local terrain refinement elsewhere. The follow-up also samples two lower-screen rays and retains the last valid terrain hit when all rays miss. It records the focus source (`center`, `lower`, `retained`, or `fallback`) and cumulative tabletop focus changes for on-headset validation. The JSON cannot prove the exact ray hit in those earlier screenshots because those fields were not yet recorded.

The next Putrid Pete tabletop trace on `74ffc3d` lasted 87.5 seconds with Cesium Bing active. It recorded **1,544 new imagery patches, 1,532 disposed patches, and 72 tabletop terrain focus changes** after the first one-second window, with zero tile-cache failures. The lower-screen ray was the focus source for most of the session. This is excessive churn, so `10fad82` uses a lower-screen ray only when the center ray misses. A matched on-headset retest is still required to determine whether churn falls and the ridgeline remains sharp.

The Enchantments and Dragontail screenshots at 09:32:22 and 09:32:31 Pacific time match the `bedc810` trace from 09:31:22–09:32:37, **not** the later Putrid Pete trace. At both screenshot moments, the first-person view had all 64 selected imagery patches resident, 100% selected high-resolution coverage, zero requests in flight, and about 72 callbacks/s. The screenshots nevertheless show smooth, blurry side walls and ridges. The first-person selection code spent its bounded patch budget on the trail corridor and ignored head direction; only one local high-resolution terrain chunk was visible, so farther faces also used the coarse base mesh. Build `10fad82` gives priority to the hiker's immediate surroundings and sampled visible terrain before off-screen corridor prefetch, and records `firstPersonViewSamples` and `firstPersonHighResSamples` per window. This is an imagery-selection improvement, not proof that distant mesh detail is solved; verify both imagery and terrain shape in the same headset viewpoint.

A new Enchantments run at 09:48 on `74ffc3d` again showed blurry side walls at the same lake viewpoint. The trace had 100% selected coverage, zero in-flight requests, and approximately 72 callbacks/s at both screenshot times. That run had kept an older browser page open; the local server was already serving `10fad82`.

The user then reloaded and repeated the Enchantments run on **`10fad82`**, lasting 92.7 seconds with Quest High and Cesium Bing. The visible-terrain samples were typically 4–5/6 at z19. Within a second of the 09:51:59 screenshot, the sampled z19 count dropped to **0/5**, selected coverage to 14%, draw calls to 22, and callback cadence to 41.8/s while six requests were in flight. Across the run, 1,505 patches were created and disposed after the first one-second window. The screen still had broad blurry faces even in later fully loaded windows. This view-following tile footprint churns too much and leaves distant base terrain coarse. The next change replaces view-following Quest High selection with a stable 360-degree z16–z19 tile hierarchy around the hiker, using at most 61 of the existing 64 patch slots. Head rotation will not change the selected tile keys. Its visual and device performance remain to be verified on the headset.

These JSONs measure browser callbacks and main-thread work through WebGL submission. They do **not** provide compositor-delivered FPS, GPU frame time, reprojection/stale-frame count, battery temperature, or thermal throttling. Quest Browser did not expose an XR target refresh rate to the recorder, so missed callbacks cannot be counted reliably. OVR Metrics Tool or Meta's WebXR performance tooling is needed before claiming that either preset meets a device frame-rate target over a longer session.

Keep High as the fidelity default and Balanced as an explicit performance option. Profile the terrain raycast, patch reconciliation, and rendering costs within High; then remove redundant work without shrinking its imagery footprint or terrain shape. Repeat a controlled sequence with comparable movement, a longer duration, and device GPU/FPS/thermal metrics before declaring a sustained performance target met.
