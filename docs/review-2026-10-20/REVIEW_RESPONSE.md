# Response to the second architecture review

The user supplied this review during the terrain-loading work after `55ba5eb` (published application `e8f0d28`). Its central concern is supported: hundreds of separate imagery patches create substantial submission, geometry preparation and replacement work. The [failed Bing run](../review-2026-10-19/NATIVE_BING.md) still has 1,086 peak aggregate Three.js draw calls and extensive patch replacement. A different imagery provider did not resolve subjective acceptance. Improving the renderer and restoring visible terrain detail remain priorities; the changes below are bounded fixes, not an accepted replacement architecture.

## Findings checked against code and evidence

| Review finding | Assessment and action |
| --- | --- |
| Independent clipped imagery meshes and materials impose excessive work | Supported by the implementation and captured submission costs. Move toward compatible tile batching and coordinated terrain/imagery ownership. Preserve geographic UVs, mip boundaries, fading/overlap, lit relief and broad High coverage. A universal device draw-call ceiling or a promised sub-50-call result is not established by these captures. |
| HUD force redraws bypass the 85 ms limit | Reproduced. A controlled production-browser replay produces 1,441 upload requests for 720 hover/drag events. All redraw causes now share the cap; the same replay produces 12 requests, including the final display update. Callbacks and session state still change immediately. Logical RGBA source bytes are not measured GPU transfers. |
| 39.4 FPS characterizes the entire 154-second baseline | That value is the mean browser FPS sample from the separately marked **eight-second runtime trace**. It is not an average over the full MR report. The later Bing report has callback/submission measurements but no new GPU/compositor trace. The [original report](../review-2026-10-19/NATIVE_TABLETOP.md) and [Bing report](../review-2026-10-19/NATIVE_BING.md) retain these distinctions. |
| MeshBasicMaterial immediately saves about 60% | No matched shader benchmark supports that percentage. It also removes terrain lighting that supplies relief cues, a concern explicitly raised by the user. Evaluate a cheaper lit material or controlled unlit comparison alongside batching; do not switch the entire app based on a predicted percentage. A material change alone does not reduce mesh submission count. |
| The 1e-7 near plane explains the failed native run | `SceneManager.updateCameraClipping` enables that scaled inspection policy only for **desktop diorama**, outside XR. The tabletop far plane is bounded from the model extent with a minimum of 10; 80,000 is the separate walking/XR path, whose near is 0.1. Desktop precision at extreme zoom still deserves evaluation, but this is not the native path described by the review. A fixed 5 mm desktop floor would clip existing close inspection at small model scales. |
| Two Earth radii necessarily cause terrain/imagery drift | The local scene conversion has an inverse; imagery and DEM sample the same geographic coordinates through their own mappings. The presence of different radii alone does not establish misregistration. Local distance/projection distortion and geographic registration are separate concerns. Preserve existing UV/triangle parity tests when evaluating ENU or a conformal projection. The earlier reproduced 3DEP extent adjustment bug was corrected independently. |
| One NoData sample discards an otherwise useful USGS raster | Correct. The saved failed Bing overview has complete coverage, so this rejection does not explain that particular overview. The later [rendered-footprint correction](../review-2026-10-21/TERRAIN_FOOTPRINT.md) retains valid high-resolution terrain when NoData is outside the mesh's complete guarded bilinear support, with exact-mask worker checks and no invented heights. Interior voids and whole-model coverage remain open. |
| One FIFO worker can delay decoding behind mesh preparation | Correct. Its single active job and reusable surface snapshots bound CPU and transient copies. Queued jobs survive an active-job abort; they are not all running and killed together. The 5,000 ms value is a startup **timeout**, not a normal five-second delay. A two-lane/pool design needs job ownership, source-cache routing, cancellation, memory limits and measured latency. An abort message alone cannot interrupt a synchronous clipping loop without yielding. |
| WebXR quad layers improve spatial UI | A useful platform-specific prototype after upload throttling. Runtime feature detection, fallback, canvas-to-layer updates, input hit planes, reference-space resets and lifecycle tests are required. No implemented quad-layer path or native clarity improvement is claimed here. See Meta's [WebXR layers documentation result](https://developers.meta.com/vr/blog/achieve-better-rendering-and-performance-with-webxr-layers-in-oculus-browser) and [performance workflow](https://developers.meta.com/vr/documentation/web/webxr-perf-workflow). |
| Raise default exaggeration and enable shadows to restore detail | These alter presentation or rendering cost, not source/mesh detail. Keep the user's exaggeration control and physical 1x default while resolving missing refinement and coarse coverage. Lighting/shadow changes require a visual and GPU comparison; they do not close the DEM regression. |
| Large classes, UI duplication and two terrain streamers complicate maintenance | Supported. Incremental extraction is appropriate, starting with renderer ownership and shared presentation policy. Existing playback presentation, landmarks and XML parsing are already shared. Preserve the legacy fallback until replacement behavior and transitions are covered. File length alone is not a measured frame bottleneck. |

## Work selected from this review and the ongoing investigation

First, remove reproduced unnecessary work: strict HUD upload coalescing, completed-DEM scheduling, and reuse of validated terrain across imagery-preparation retries. The [matched production-browser results](TERRAIN_READINESS.md) cover these changes with the actual bundled terrain worker and explicitly controlled source completions.

Next, prototype compatible imagery batching before changing High's limits or replacing the complete engine. Compare draw submission, geometry/texture memory, geographic UVs, normals/lighting, overlap/fade ordering, view changes and a native full-tour run. Treat the prototype as an experiment until it preserves appearance and broad coverage. Unified hierarchical terrain/imagery ownership is the architectural direction; it is not a completed migration or a promise of 72 Hz.

Keep partial DEM coverage, worker job separation, desktop depth precision and quad layers as separately measurable follow-ups. Defer new first-person features under the user's existing diorama priority. No new native run or overall visual/performance acceptance has been obtained for this checkpoint.
